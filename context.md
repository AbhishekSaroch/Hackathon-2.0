**Judging (same 5 questions for every team):** does it work, technical depth, can you explain it simply, would we use it on Monday, have we seen this before.

**BI-02 acceptance criteria:** Macro-F1 >= 0.75 on a hidden set, and correct abstention ("insufficient evidence") on the ambiguous cases. **BI-03:** precision in the top 5% flagged >= 3x the base rate, and median lead time >= 21 days before the first missed EMI, strictly point-in-time.

## 2. Important: all data is synthetic

Organizers do not give us test data, so **every number in the DB is generated by us** (`backend/data/generate_synthetic.py`, seed 42). Scores on it prove the *method*, not real-world accuracy. The UI footer says so too. There is no real customer data anywhere.

## 3. How BI-02 works (one paragraph)

For each late account the agent: (1) pulls repayment history, promises, call transcripts and the bank statement from the DB tools; (2) **AI reads the calls** and extracts what the customer *says* ("job chali gayi") with a verbatim quote; (3) **Python computes the numbers** (salary drop %, months since last salary, balance vs EMI, double debit and its timing, promise kept ratio); (4) **AI tests the claim against those numbers** and returns label + confidence + cited evidence; (5) if the statement is thin or confidence < 0.70 it asks for a **fresh statement** (once) and re-decides; (6) if confidence is still < 0.55 it **abstains** ("Not sure"); (7) **Python rules** pick the next action; (8) a templated English note is written and everything is saved to the DB. Nothing is ever sent to a customer: recommendations wait for a human to approve.

```
DB tools -> evidence numbers (Python) -> AI reads calls -> AI decides (label, confidence, evidence)
         -> fresh statement if unsure -> abstain if still unsure -> rules pick next action -> save
```

**Labels:** `forgot`, `cant_pay`, `wont_pay`, `disputed`, `insufficient` (shown as "Not sure").

**Next-action rules (code, the AI cannot override):**

| Label | Action |
|---|---|
| forgot | WhatsApp reminder, no dues pressure |
| cant_pay | Telecall: easy payment plan / EMI restructure |
| wont_pay | Senior collector call; **field visit only if** DPD >= 90 and outstanding >= Rs 5 lakh and confidence >= 0.8 |
| disputed | Dispute team, pause collection calls |
| insufficient | Human collector talks to the customer |
| (account is current) | Service nudge only, never calls or visits |

## 4. Design decisions worth knowing

- **AI for language and judgement, Python for numbers and safety.** The AI never does arithmetic and never picks the channel.
- **Manager-facing text is templated in code, not written by the LLM.** We tried LLM-written notes and twice they flipped a fact (said the balance was below the EMI when it was not). In collections a wrong fact is the worst outcome. Notes are English; customer quotes stay verbatim (their own words).
- **Citations are validated in code.** Every evidence item must reference a real call id, transaction id or fact name we supplied, otherwise it is dropped.
- **Privacy by design:** the LLM never gets the customer name or the raw statement, only computed numbers and short transcripts. No protected attributes (age, gender, religion, caste, location) are used anywhere.
- **Tenant isolation is enforced in the query layer** (`backend/db/db.py`): a query without the `:tenant_id` placeholder is refused. Another lender id sees nothing.
- **Reproducible:** temperature 0, fixed seed, and an on-disk cache of LLM answers (`backend/llm/cache`).
- **Abstaining is a feature.** If the customer gave no reason and income is irregular, confidence is capped at 0.5 in code, so the agent says "Not sure" instead of guessing.

### BI-03 results (synthetic data, read the caveats)

How it is measured: the system runs daily like in production with a fixed alert threshold, set from public-period scores only so that about 5% of accounts ever cross it. Flags may start 30 days before the evaluation window (the real system does not reset); only misses inside the 60-day window count. Precision = share of flagged accounts that then miss an EMI; lift = precision / base rate; lead = days from first flag to DPD 1.

| Hidden period (days 91-150) | Lift in the top 5% flagged | Precision (base rate 2.6%) | Caught | Median lead |
|---|---|---|---|---|
| **Model** | **16.9x** (95% CI 15.0-18.9) | 45% | 128 of 154 (83%) | **29 days** (CI 24-32; 25th percentile 12) |
| Hand-written rule, no learning | 6.1x | 16% | 60 of 154 | 17 days |
| Random flagging, same 5% budget | 1.1x | 3% | 9 of 154 | n/a (9 hits) |

The public-data rehearsal predicted this (17.6x, 30 days), so there is no sign of overfitting. **Caveats to say out loud:** (1) the data is synthetic and easier than real life (even a simple rule gets 6x), so these numbers show the method, not real-world accuracy; (2) the hidden period is not a perfectly untouched test: the ledger records one formal look, but earlier we tuned the generator's difficulty using quick diagnostics that scored the hidden window (the first data version gave 0.7x, so we loosened noise); (3) we found and fixed two measurement mistakes before the hidden run (an alert protocol that accumulated flags until random flagging looked good, and a window that cut off lead time), using public data only; (4) 12% of defaulters give no warning by design.

**BI-03 commands.** Build data: `python backend/data/generate_bi03.py` then `python backend/data/load_bi03.py --reset`. Train: `python backend/agents/bi03/backtest.py train`. Replay the stream: `python backend/agents/bi03/runner.py replay --from 61 --to 150 --reset`. All BI-03 tests (each exits 1 on failure): `backend/tests/test_bi03_features.py`, `test_bi03_mutations.py`, `test_bi03_model.py`, `test_bi03_runner.py`, plus `check_bi02.py` for BI-02. Runner notes: an account is "current" until an EMI stays unpaid past the 4-day grace period; a flag repeats only after the 30-day cooldown if the account is still above the threshold (524 flags on 371 accounts in the replay); the first replay day flags 103 accounts because there is no earlier state.

## 10. Known limits

- **Groq free tier:** 8,000 tokens/minute per model and 200,000 tokens/day on gpt-oss-120b. One account costs about 3,000 tokens, so roughly 65 accounts/day. We hit this and the UI hung; `groq_client.py` now has a rate limiter and fails fast (error instead of hanging) when the wait would exceed 45 s. **The brief's "5,000 accounts in under an hour" is not reachable on the free tier**: it needs a paid tier or the organizers' key, plus a rules-first shortcut for clear cases. Say this openly in the demo.
- The Approve / Skip button is tested through the API, not clicked in the UI. Minor UI nit: "1 calls" should be "1 call". There is no real compliance gate yet (it belongs to BI-03).
- **Real-world note for Q&A:** a lender normally does not hold a customer's bank statement. In production it comes through an **Account Aggregator** with the customer's consent (the brief lists "AA statement (mock)" as a tool and gives D8 as data). Without a statement the agent says "Not sure" and sends a human. Groq is a third-party cloud, so real customer data would need an approved or self-hosted model. Position it as consent-based and **compatible with RBI's framework, pending compliance sign-off**, not as "RBI compliant".

**Synthetic-world rule to remember:** an EMI paid up to 4 days after its due date counts as "paid in the grace period" and is not a DPD 1 event; "went DPD 1" means an EMI that stays unpaid. **Biggest risks:** point-in-time leakage (disqualifying), reaching 3x lift, and the fact that our own synthetic data makes the numbers a method demo, not real-world proof.

## 12. Glossary

DPD: days past due. Bucket: DPD range (1-30, 31-60...). NPA: very late loan. AA: Account Aggregator, the consent-based way to fetch bank statements. D1 / D3 / D5 / D6 / D8 / D9 / D11: the brief's datasets (accounts, repayments, calls, promises, statements, bureau, service templates). Macro-F1: average of per-label F1 scores, so small classes count equally. Abstain: answer "not sure" instead of guessing. Point-in-time: a model may only use data that existed on the day it predicts.

## 13. LC-04 (Command center): built, with the honest hidden result

**What it is.** A role + a plain-language request builds a dashboard spec (metrics, charts, filters) from 59 governed metrics; a seasonality-aware detector watches 8 key metrics on a 15-minute cube; a drill-down names the driving segment and proves it (counterfactual); alerts are two templated lines + a link to the annotated view (mock, nothing is sent); a role layer limits every number to the user's lenders / metrics / dimensions. UI: sidebar group 3 (Command center, Incidents, Metric catalog, Scorecard), a "Viewing as" switcher, a replay clock ("Advance 15 min", jump chips).

### 14.9 Ask also reads the other modules' data (added 2026-11-20)
* **Copy, not a link.** `python backend/data/sync_all.py` copies every tenant-scoped table of BI-02 (`portfolioiq.db`), BI-03 (`bi03.db`) and LC-04 (`lc04.db`) into `backend/ask_all.db` (git-ignored, about 310 MB, 40 tables, 2.9 M rows, about 15 s) with prefixes `bi02_`, `bi03_`, `lc04_`. The sources are opened with SQLite `mode=ro`; nothing is changed or deleted in them. The new file is built beside the old one and swapped in only when every row count matches. Answer keys and contact logs (`gold_labels`, `outcome_labels_hidden`, `anomaly_key*`, `outreach_log`) are never copied. The LC-01 warehouse is not copied (Ask keeps reading `lc01.db`, so the hidden evaluation is untouched).
* **Routing by code, no model.** `lc01_sources.py` has 14 extra metrics (BI-02: accounts by non-payment reason, recommended actions, promise kept rate, delinquent accounts, outstanding; BI-03: flags, flag hit rate, lead time, nudges, watched accounts; LC-04: anomalies, alerts, accounts, outstanding, dashboards), English and Hinglish aliases, and value words ("forgot", "bhool", "paise nahi de rahe"). It runs after the same `precheck` (injection, raw SQL, writes, other lenders) and before the lender-warehouse flow, which is unchanged. A question that matches nothing falls through exactly as before.
* **Access follows the user record.** `u_abc` (ABC Bank, role lender_user, tenant `abc_bank`) reads BI-02 and BI-03; `u_cn` (role cn_leader) reads LC-04 (tenants GLOBAL, L1 to L5, which are NOT the lenders of the lender warehouse); the five original users read none of them, and an explicit mention ("early warning", "command center") is refused as out of scope. Every statement is assembled from fixed fragments, checked by `check_sql` with a per-source table whitelist (no calls, repayments, events or label tables), and run through `db.py` with the tenant id bound there.
* **One non-obvious counting rule.** BI-02 `assessments` can hold a second assessment for the same account (re-run), so "accounts by reason" counts each account once, by its latest assessment: forgot 13, cannot pay 13, will not pay 9, insufficient 11, disputed 14 (60 accounts, not 61 rows).
* **Honest limits.** The copy is a snapshot: after BI-03 "advance one day" or an LC-04 replay, press "Refresh data copy" (POST /lc01/sync) or run sync_all.py. Only assessed BI-02 accounts have a reason (60 of 300). No root-cause explanation for these metrics, no account lists. The 14 metrics are checked against independent calculations on the same copy (tests/test_lc01_sources.py); they are not part of the 45/50 hidden score.
* **One demo user (2026-11-20).** The app offers only `u_neha` (Neha Kapoor, Collections Head, role collections_head): lender warehouse L1 to L3 plus BI-02, BI-03 (tenant abc_bank) and LC-04. `UI_USERS` in lc01_access.py controls this; `u_l1`...`u_cn` stay for tests and the evaluation.
